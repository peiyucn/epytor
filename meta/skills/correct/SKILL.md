# Correct

> 触发：同一类错误第二次出现；owner 反复纠正；一个检查本该拦住却没拦住。
> 不触发：一次性小问题；没有证据的“我觉得要注意”。

## 输入 / 权限

- 输入：重复纠正记录、失败检查、revert / 返工、review finding；
- 权限：改检查/规则须 owner 批准；不自己合并。

## 目标

不是再写一条规则，而是**让下一次不可能再犯**。

## 步骤

### 1. 收集证据

- 最近被 owner 纠正的地方；
- revert、返工、review 里重复出现的 finding；
- 本该失败却通过的测试/检查；
- 被跳过的 playbook 步骤。

把现象按“错误类”分组；同一类出现两次以上才算。

### 2. 在最高层修

按顺序，能高就不低：

1. **架构/API**：让错误写法没有入口，或状态只有一个 owner；
2. **类型**：让非法状态写不出来；
3. **lint/CI**：让错误代码过不去；错误信息要指出正确写法；
4. **测试**：让行为回归变红；
5. **文档/AGENTS**：只留给真正需要判断、无法自动化的内容。

不要先改 AGENTS。

### 3. 证明检查有效

- 先写负例，证明检查会红；再实现检查，证明当前正常仓库会绿；
- 新检查必须在一个真实的历史错误上失败；
- 修复后同一个检查通过；
- 接入标准命令：代码规则进 `npm run lint:code`，仓库策略进 `npm run lint:policy`，再接入 `verify` 和 CI；
- 本地和 CI 跑同一条命令；
- 删除已被检查完整覆盖的文字说明；单独提交，不混入无关功能；
- 例外写在出错行上：原因、过期时间、owner 批准。

### 4. 更新规则与执行

在对应规则文件（engineering / repo-settings / verification）里写清：

- 哪条规则；
- 现在由什么执行；
- 证据是什么。

规则索引见 [rules/README.md](../../rules/README.md)。

如果规则已经存在但没有任何东西执行它，这就是 repeat，必须当场升级。

### 5. 删除失效规则

错误已经不可能发生时，删掉对应规则或说明，避免 AGENTS/rules 继续膨胀。

## 检查

- 负例先红，正例后绿；
- 检查接入标准命令和 CI；
- 规则/执行已更新；
- 失效规则已删除。

## 输出

```text
错误类：
证据：
选了哪层：
新增/修改的检查：
规则/执行变化：
删除了什么：
未解决/未验证：
```

## 边界

- 先修问题，不要只解释；修复优先于说明；
- 可以提议改规则/检查，但不能自己合并；owner 批准后才生效；
- 不把这次事故的故事写进规则，写原则；
- 结构性修复优先于文字提醒。
